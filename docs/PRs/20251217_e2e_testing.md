## Objective

Implement comprehensive end-to-end (E2E) testing infrastructure using Playwright to validate critical user flows and ensure core business functionality works correctly across the entire application stack. This addresses the need for integration testing beyond unit tests, catching issues that only appear when all components work together.

## Test Environment Requirements

### Prerequisites

Before running E2E tests, ensure:

1. **Test users exist in database:**

   ```sql
   -- Customer: customer@test.com / Customer123!
   -- Staff: staff@test.com / Staff123!
   -- Manager: manager@test.com / Manager123!
   -- Admin: admin@test.com / Admin123!
   ```

2. **Test menu items seeded:**
   - At least 3-5 menu items across different categories
   - Items should have name, price, description, category

3. **Environment variables configured:**

   ```bash
   NEXT_PUBLIC_SUPABASE_URL=https://test-project.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=test-anon-key
   SUPABASE_SERVICE_ROLE_KEY=test-service-key
   ```

4. **Playwright browsers installed:**
   ```bash
   npm run playwright:install
   ```

### Running Tests

```bash
# Run all E2E tests
npm run test:e2e

# Run specific suite
npx playwright test customer-checkout-flow

# Interactive UI mode (recommended for development)
npm run test:e2e:ui

# Debug mode with breakpoints
npm run test:e2e:debug

# View test report
npx playwright show-report
```

## Technical Implementation Details

### Test Architecture

```
e2e/
├── helpers/
│   └── fixtures.ts          # Shared test data and utilities
├── customer-checkout-flow.spec.ts   # Customer E2E tests
├── staff-order-workflow.spec.ts     # Staff E2E tests
├── manager-menu-management.spec.ts  # Manager E2E tests
└── README.md                        # E2E documentation
```

### Key Design Patterns

1. **Page Object Pattern (Helper Functions)**
   - Encapsulated common actions (login, navigate, add to cart)
   - Reusable across test suites
   - Maintainable when UI changes

2. **Test Data Fixtures**
   - Centralized test users and menu items
   - Consistent data across tests
   - Easy to update

3. **Explicit Waits**
   - `waitForLoadState('networkidle')` for page loads
   - `waitForResponse()` for API calls
   - Timeout strategies for flaky operations

4. **Role-Based Testing**
   - Separate test suites per user role
   - Access control verification
   - Real-world user journey simulation

### Selectors Strategy

Tests use robust selectors prioritized as:

1. `data-testid` attributes (most stable)
2. Semantic role selectors (`role="button"`)
3. Text content selectors (`:has-text()`)
4. CSS classes (least stable, avoid when possible)

### Error Handling

- Screenshots captured on failure
- Trace files for debugging
- Retry logic in CI (2 retries)
- Explicit timeout configurations

## Known Limitations

### Test Data Dependencies

- **Requires seeded database** - Tests expect specific users and menu items to exist
- **Not fully isolated** - Tests may affect shared database state
- **Manual cleanup** - Database should be reset between full test runs

**Recommendation**: Use separate test database or implement database snapshots/restore between CI runs.

### Selector Fragility

- Some selectors use text content (`:has-text()`) which may break with UI copy changes
- Not all components have `data-testid` attributes yet

**Recommendation**: Add `data-testid` attributes to critical UI elements in future PRs.

### Network Dependencies

- Tests require dev server running (auto-started by Playwright)
- API calls to real Supabase instance (mocking not feasible for E2E)

## CI/CD Integration

### GitHub Actions Workflow

Add to `.github/workflows/ci.yml`:

```yaml
- name: Install Playwright Browsers
  run: npx playwright install --with-deps chromium

- name: Run E2E Tests
  run: npm run test:e2e
  env:
    NEXT_PUBLIC_SUPABASE_URL: ${{ secrets.TEST_SUPABASE_URL }}
    NEXT_PUBLIC_SUPABASE_ANON_KEY: ${{ secrets.TEST_SUPABASE_ANON_KEY }}
    SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.TEST_SUPABASE_SERVICE_KEY }}

- name: Upload Playwright Report
  if: always()
  uses: actions/upload-artifact@v3
  with:
    name: playwright-report
    path: playwright-report/
    retention-days: 30
```

### Branch Protection

- E2E tests run on PR to `dev` and `main`
- Must pass before merge allowed
- Parallel execution with unit tests (Jest)
